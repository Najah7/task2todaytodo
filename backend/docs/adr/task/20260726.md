# Task Management Implementation Notes

This is a short memo for the task management API implementation.
Detailed prompts remain in the root `prompt_*.md` files.

## Shape

```text
User
|-- Projects
|   `-- Tasks
`-- Tasks
    |-- TodoItems
    `-- TaskSchedules
```

- User -> Projects (To group long-running work for a user)
- User -> Tasks (To manage standalone tasks for a user)
- Project -> Tasks (To group tasks under a project)
- Task -> TodoItems (To break down a task into smaller units of work)
- Task -> TaskSchedules (To schedule a task at a specific time)
- PriorityMaster -> Projects/Tasks (To share priority values across planning levels)
- FrequencyMaster -> TodoItems/TaskSchedules (To share repeat weekday values)

## Core Decisions

```text
HTTP PATCH
    -> partial input
Service
    -> merge allowed fields only
Repository Update
    -> full entity persistence
DB
```

- All user-owned APIs require authentication.
- Ownership is enforced simply in SQL by `user_id` or by joining through `tasks.user_id`.
- READs that cross tables return Aggregates:
  - `ProjectAggregate = Project + Tasks`
  - `TaskAggregate = Task + TodoItems + TaskSchedules`
- Todo generation is out of scope here; this implementation prepares the structured source of truth.
- `progress` is system-managed and not user-updatable.
- Project and Task priority default to `low`.
- Tasks created under a Project inherit Project priority when task priority is omitted.
- Project scheduling uses `start_at` and `end_at`; Projects do not store `due_date`.
- `due_date` is date-only and belongs to Tasks and TodoItems.
- `due_date: null` resets Task due dates through PATCH.
- `interval_weeks = 0` means one-off and is the create default for TodoItems and TaskSchedules.
- TaskSchedules use `start_at` and `end_at`; due dates are not stored on schedules.
- TodoItems expose check/uncheck, not generic update.
- SQL files are split by intent:
  - `*.query.sql` for READ
  - `*.mut.sql` for WRITE
- Generated files are updated from sources only:
  - sqlc output from `backend/db/queries`
  - Swagger output from handler annotations

## API Surface

```text
Projects
|-- POST   /api/projects
|-- GET    /api/projects/{project_id}
|-- PATCH  /api/projects/{project_id}
`-- DELETE /api/projects/{project_id}

Tasks
|-- POST   /api/tasks
|-- POST   /api/projects/{project_id}/tasks
|-- GET    /api/tasks/{task_id}
|-- PATCH  /api/tasks/{task_id}
|-- PATCH  /api/tasks/{task_id}/priority
|-- PATCH  /api/tasks/{task_id}/estimation
`-- DELETE /api/tasks/{task_id}

TodoItems
|-- POST   /api/tasks/{task_id}/todo-items
|-- POST   /api/tasks/{task_id}/todo-items/{todo_item_id}:checked
|-- POST   /api/tasks/{task_id}/todo-items/{todo_item_id}:unchecked
`-- DELETE /api/tasks/{task_id}/todo-items/{todo_item_id}

TaskSchedules
|-- POST   /api/tasks/{task_id}/schedules
|-- PATCH  /api/tasks/{task_id}/schedules/{task_schedule_id}
`-- DELETE /api/tasks/{task_id}/schedules/{task_schedule_id}
```
